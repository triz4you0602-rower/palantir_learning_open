# 케이스: 대중 자료 vs 1차 문서 대조 검증 (Case: Source Verification)

> 이것은 **실제로 수행된 케이스**다 (2026-07-14). 이 저장소의 `knowledge/03-ontology.md` §4 기술 용어를 팔란티어 공식 docs로 검증한 과정을, FDE 5단계 렌즈로 되짚는다. 지식을 만드는 활동 자체가 하나의 "배포"였고, 여기서 방법론을 메타적으로 훈련한다.

- **도메인:** 지식 베이스 신뢰성 (내부 문서 품질)
- **날짜:** 2026-07-14
- **한 줄 요약:** 오픈소스 책으로 심화한 온톨로지 기술 서술이 실제 스펙과 맞는지 1차 문서로 검증해, 우리 지식의 그라운드 트루스를 확보한다.

---

## 1단계 · 몰입 (Immerse) — 현실 지도

- **누가** 결정: 이 저장소로 학습할 미래의 사용자(그리고 Claude)가 `03-ontology.md`를 "사실"로 믿고 판단·실습한다.
- **무엇을** 근거로: `03`의 §4 서술 — 그런데 그 출처는 **오픈소스 책·블로그(2차 자료)** 였다.
- **실제 프로세스:** 심화 작성 시 책의 서술을 빠르게 옮겼고, 기술 스펙의 정확성은 아직 검증 전이었다.

### 숨은 곳 3가지
- 📌 **문서화 밖 결정:** "책이 잘 정리했으니 맞겠지"라는 **암묵적 신뢰** — 어디에도 근거로 적히지 않은 가정.
- 📌 **기록 안 되는 데이터:** 각 문장이 *어느 출처의 몇 차 자료*인지 추적이 안 됐다. 2차 자료와 1차 스펙이 뒤섞여 구분 불가.
- 📌 **하중 임시방편:** "그럴듯한 정확함(plausible precision)" — MDO·Action Log 같은 구체 용어가 오히려 **틀린 내용에 신뢰를 부여**하는 임시방편처럼 작동.

---

## 2단계 · 문제 정의 (Frame) — 문제 진술서

- **문제 진술:** 우리 지식 베이스의 기술 서술이 2차 자료에 의존해, 대규모로 학습에 쓰이기 전에 **1차 스펙과의 정합성이 검증되지 않았다.**
- **연결되는 결정/행동:** "이 문서의 §4를 사실로 인용/실습에 사용할 것인가"라는 반복되는 결정.
- **성공 지표:** §4의 각 주장에 대해 (a) 1차 문서 근거 링크 확보, (b) 판정(✅/⚠️/❌) 부여, (c) 오류 정정 반영 — **미검증 주장 0건.**
- **실제 제약:** 실제 Foundry 접근 없음 → 공개 `palantir.com/docs`가 도달 가능한 최상위 1차 자료. 시간 제약상 §4(기술 용어)에 범위 한정.
- **옳은 문제인 근거:** 잘못된 사실 하나가 이후 모든 케이스·판단에 복리로 전파됨. 검증은 **결정에 직접 연결**되고 측정 가능.

> 안티패턴 점검: 처음엔 "온톨로지를 더 화려하게 심화"가 목표였음(=범위 팽창). "**어떤 결정이 이 정보에 의존하나?**"를 물어, "인용해도 되는가"라는 실제 결정으로 문제를 좁혔다.

## 3단계 · 온톨로지 스케치 (Model)

검증 활동 자체를 온톨로지로 모델링하면, "결정→행동→기록" 루프가 왜 필요한지 체득된다.

### Object Types
| Object Type | 주요 Property | 의미 |
|---|---|---|
| Claim (주장) | 문장, 출처유형(1차/2차), 판정(✅/⚠️/❌) | §4의 개별 기술 주장 |
| Source (출처) | URL, 유형(공식docs/책/블로그), 신뢰등급 | 근거 자료 |
| Correction (정정) | 이전값, 정정값, 근거 | 오류 수정 기록 |

### Link Types
| From | Link | To | 의미 |
|---|---|---|---|
| Claim | citedBy | Source | 주장이 어떤 출처에 근거하나 |
| Claim | resultsIn | Correction | 검증이 정정으로 귀결 |

### Action Types
| Action | 무엇을 바꾸나 | 어떤 결정을 실행하나 | 부수효과 |
|---|---|---|---|
| verifyClaim | Claim.판정, Claim.출처유형 갱신 | "이 주장을 인용해도 되는가" | Correction 생성(필요 시) |
| recordCorrection | Correction 생성 + 문서 반영 | 오류를 지식에 되먹임 | 부록 A 표에 1행 추가 |

> 포인트: `recordCorrection`이 없으면 검증 결과가 소실되고(=1단계의 숨은 곳), 다음 사람이 같은 오류를 반복한다. 이 Action이 루프를 닫는다.

## 4단계 · 자갈길 구축 (Build) — 실제 수행

- **접근:** 완벽한 검증 파이프라인(고속도로)이 아니라, §4 주장별로 공식 docs를 병렬 조회 → 판정 → 정정하는 최소 절차(자갈길).
- **산출물:** [../../knowledge/03-ontology.md](../../knowledge/03-ontology.md) §4 인라인 정정 + **부록 A 검증표**.
- **핵심 발견 (정정된 오류):**
  1. ❌ **Function = 읽기 전용** → 사실은 ontology edits로 상태 변경 가능. "함수가 읽기전용이라 AI 안전"이라는 널리 퍼진 서술이 **틀림.** 실제 안전 근거 = 정의된 Action 범위 + Branch Proposal 리뷰.
  2. ❌ **Action Log가 대상과 1:1** → 사실은 **1:N** (제출 1건당 로그 1개가 영향 객체 여럿에 FK). before/after는 별도 edit history.
  3. ⚠️ **링크 자체에 임의 속성** → object-backed link(중간 객체 타입)로만.
  4. ⚠️ **MDO** → 컬럼 방향만, row-wise 미지원 등 정밀 제약.
- **제약 처리:** Foundry 미접근 → 공개 공식 docs로 대체. 출처를 "개념/전략(2차) vs 기술 스펙(1차)"으로 **분리 표기**해 추적성 확보.

## 5단계 · 패턴 추출 & 회고 (Extract)

- **반복될 추상:** "**Claim–Source–Correction** 루프"는 이 저장소의 *모든* 지식 문서에 재사용 가능한 패턴이다. 앞으로 `knowledge/`에 사실을 추가할 때 이 렌즈로 검증한다. (자갈길에서 발견한 고속도로 후보)
- **승격 후보:** 각 knowledge 문서 하단에 "부록: 공식 대조 검증표"를 표준 섹션으로. `CLAUDE.md`의 "출처 필수" 규칙과 결합.
- **배운 것:**
  1. **그럴듯한 정확함이 가장 위험하다.** 구체적 전문 용어일수록 검증 없이 신뢰하기 쉽다.
  2. **2차 자료는 큰 그림에, 1차 문서는 스펙에.** 둘의 역할을 섞지 말 것.
  3. 이것은 FDE의 **그라운드 트루스** 원칙 그대로다 — "그들이 말한 프로세스"(책)가 아니라 "실제 프로세스"(공식 스펙)를 확인. → [../../knowledge/02-problem-solving-playbook.md](../../knowledge/02-problem-solving-playbook.md)
- **다음엔 무엇을 다르게:** 심화 *작성 시점*에 출처유형(1차/2차)을 문장 단위로 태깅했다면, 사후 검증 비용이 줄었을 것. → "쓰면서 검증"을 기본값으로.
- **걸려든 안티패턴:** ⑴ *과잉 일반화* 위험 — 책 하나로 스펙을 단정. ⑵ 초기 *범위 팽창*("더 화려하게") → "어떤 결정에 쓰이나?"로 교정.
