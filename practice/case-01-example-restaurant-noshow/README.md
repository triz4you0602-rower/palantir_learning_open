# 케이스: 레스토랑 노쇼(no-show) 손실 줄이기 (Case: Restaurant No-show)

> ⚠️ 이것은 **워크된 예시(worked example)** 다. 방법론을 어떻게 적용하는지 보여주기 위한 가상 케이스이며, 실제 배포가 아니다. 새 케이스를 만들 때 이 흐름을 참고하라.

- **도메인:** 외식업 (예약제 파인다이닝 3개 지점)
- **날짜:** 2026-07-14
- **한 줄 요약:** 예약 노쇼로 인한 좌석 공실 손실을, 결정 가능한 운영 행동으로 전환한다.

- [x] **2. 건물 밖으로 나갔나** — 예약 시스템 화면이 아니라 홀의 종이 노트·매니저의 감까지 현장에서 확인. → §1
- [x] **3. 중개 계층이 없나** — 문제를 겪는 매니저와 해결 설계를 직접 연결, 별도 요구사항 문서 중개 없음.

- [x] **5. 자갈길 먼저인가** — 규칙 기반 자갈길로 시작, ML 고속도로는 패턴 반복 확인 후. → §4~5

- [x] **7. 결과에서 역산하나** — 성공 지표를 "공실 좌석 수/월"이라는 결과에서 역산. → §2

## 1단계 · 몰입 (Immerse) — 현실 지도

- **누가** 결정: 지점 매니저가 매일 저녁 예약 확정/오버부킹 여부를 판단.
- **무엇을** 근거로: 예약 시스템 화면 + **매니저 머릿속의 "단골/위험 고객" 감(感)**.
- **실제 프로세스:** 시스템은 "예약 있음/없음"만 안다. 노쇼 위험 판단은 전적으로 사람 기억에 의존.
- **Mom Test 질문·답:** ("노쇼 예측 기능이 있으면 쓰시겠어요?"라고 묻지 않음 ❌) → *"지난 금요일 만석일 때 어떻게 하셨어요?"* 라고 물음 ✅ → 답: *"단골 아닌 4인 예약 두 팀에 오후에 전화 돌리고, 한 팀은 안 받아서 한 자리 오버부킹 걸었어요."* → 위험 판단이 이미 **매일 수작업으로** 일어남을 사실로 확인.

### 숨은 곳 3가지
- 📌 **문서화 밖 결정:** 매니저가 "이 손님은 지난번 노쇼했으니 리마인드 전화 두 번" 하는 규칙 — 어디에도 안 적힘.
- 📌 **기록 안 되는 데이터:** 노쇼가 발생해도 시스템엔 "취소"로도 안 남고 그냥 빈 좌석으로 흘러감. → 위험 신호가 소실.
- 📌 **하중 임시방편:** 홀 직원이 종이 노트에 "블랙리스트/주의 고객"을 적어 지점끼리 공유 안 됨. 이 노트가 사실상 유일한 위험 예측 시스템.

## 2단계 · 문제 정의 (Frame) — 문제 진술서

- **5 Whys** (표면 증상 → 근본 원인):
  1. 왜 공실 손실이 나나? → 노쇼가 발생하는데 그 자리를 못 메워서.
  2. 왜 못 메우나? → 어느 예약이 노쇼 위험인지 *예약 확정 시점에* 모른다.
  3. 왜 모르나? → 위험 정보가 시스템이 아니라 매니저 기억·종이 노트에 있다.
  4. 왜 시스템에 없나? → 노쇼가 발생해도 "취소"로도 기록되지 않아 신호가 소실된다.
  5. 왜 기록되지 않나? → **실적을 되먹이는 행동(Action)과 기록 절차가 워크플로에 아예 없다.**
  - **근본 원인:** 예측 모델의 부재(기술)가 아니라, **위험 신호를 포착·기록·공유하는 절차의 부재(조직)**. → 카프의 렌즈: "기술이 아니라 조직적."
- **리프레이밍** (① → ② → ③):
  1. *지금 문제:* "노쇼를 어떻게 예측할까?"
  2. *달리 보기:* 매니저는 이미 꽤 잘 예측한다 — 문제는 예측이 아니라 그 판단이 **휘발**된다는 것.
  3. *더 나은 문제:* "위험 신호를 어떻게 **시스템에 붙잡아 결정·행동으로** 흐르게 할까?" ← 이걸 채택.
- **문제 진술:** 노쇼 위험 정보가 사람 기억·종이 노트에 갇혀 있어, 예약 확정 시점에 오버부킹/리마인드 결정을 데이터로 내리지 못한다.
- **연결되는 결정/행동:** "이 예약에 리마인드를 몇 번 할까 / 오버부킹을 걸까"라는 **매일 반복되는 운영 결정.**
- **성공 지표:** 노쇼로 인한 공실 좌석 수 / 월, 노쇼율(%).
- **실제 제약:** 개인정보(고객 이력) 취급, 지점 매니저마다 다른 습관, 예약 시스템 API 접근 제한.
- **옳은 문제인 근거** (누구의 문제? 풀 가치?): 지점 매니저의 매일 문제이자 경영진의 매출 문제 — 이해관계 명확. 풀 가치 O: 매출 손실과 직결 + 측정 가능 + 이미 사람이 수동으로 하고 있음(수요 검증됨).

## 3단계 · 온톨로지 스케치 (Model)

### Object Types
| Object Type | 주요 Property | 의미 |
|---|---|---|
| Guest (고객) | 이름, 연락처, 과거 노쇼 횟수, VIP 여부 | 예약 주체 |
| Reservation (예약) | 일시, 인원, 지점, 상태 | 하나의 예약 건 |
| Visit (방문 실적) | 실제 방문 여부, 지연 시간 | 예약의 실제 결과 |

### Link Types
| From | Link | To | 의미 |
|---|---|---|---|
| Guest | places | Reservation | 고객이 예약을 건다 |
| Reservation | resultsIn | Visit | 예약이 방문/노쇼로 귀결 |

### Action Types
| Action | 무엇을 바꾸나 | 어떤 결정을 실행하나 |
|---|---|---|
| flagNoShowRisk | Reservation.riskScore 갱신 | "이 예약은 위험" 표시 |
| sendReminder | Reservation.reminderCount++ | 리마인드 발송 결정 실행 |
| recordVisit | Visit 생성, Guest.noShowCount 갱신 | 실적 기록 → 다음 예측에 복리로 반영 |

> 포인트: **recordVisit**가 없으면 위험 신호가 계속 소실된다(1단계의 숨은 곳). 이 Action 하나가 "데이터 → 결정 → 행동 → 다시 데이터" 루프를 닫는다.

## 4단계 · 자갈길 구축 (Build) — 최소 해결책

- **접근:** 완벽한 ML 모델(고속도로)이 아니라, 단순 규칙 기반 riskScore(자갈길)부터.
- **산출물 (가상):** `과거 노쇼횟수 >= 2 OR (금요일 저녁 AND 4인 이상)` → riskScore = high. high면 sendReminder 2회 + 오버부킹 1석 허용.
- **지탱하는 결정:** 매니저의 "리마인드/오버부킹" 결정을 규칙으로 명시화.
- **제약 처리:** 고객 이력은 집계 값(노쇼 횟수)만 사용해 개인정보 노출 최소화. 지점 간 종이 노트를 Guest 객체로 통합.

## 5단계 · 패턴 추출 & 회고 (Extract)

- **반복될 추상:** "사람 머릿속/종이에 갇힌 위험 판단"을 **Object의 Property + Action 루프**로 외부화하는 패턴 → 병원 진료 노쇼, 물류 배송 실패, 대출 연체 등 어디에나 반복됨. (= 자갈길에서 발견한 고속도로 후보)
- **승격 후보:** `riskScore + recordOutcome로 루프 닫기` 를 재사용 가능한 템플릿으로.
- **배운 것:** 진짜 문제는 "노쇼 예측"이 아니라 **"위험 신호가 시스템에 도달하지 못하는 것"** 이었다 (숨은 곳 발견이 문제 정의를 바꿨다).
- **다음엔:** 1단계에서 종이 노트를 더 일찍 발견했다면 문제 정의가 빨라졌을 것.
- **걸려든 안티패턴:** 처음엔 "ML로 노쇼 예측 대시보드"를 상상 → **대시보드 함정**. "어떤 결정으로 이어지나?"를 물어 자갈길(규칙+Action)로 되돌아옴.
- **8원칙 재채점** (0단계 대비): 1~7은 충족. **원칙 6**은 초기 대시보드 함정을 감지·교정해 결과적으로 통과. **원칙 8(복리)** 은 미충족 — 지점 간 위험 학습 공유가 없어, recordVisit를 넘어 "한 지점의 노쇼 이력이 다른 지점 예측을 개선"하도록 확장하는 것이 다음 과제.
