# 케이스: Jacobs Agua Nueva 블로워 전력 최적화 (Case: Jacobs Blower Optimization)

> ⚠️ **재구성 케이스임을 표시.** 이 케이스는 팔란티어가 공개한 impact study를 소스로 재구성했다. 원문 자체가 "All data presented herein is notional"이라고 명시하므로 **성과 수치는 예시로만 취급**한다. 오퍼레이터의 5 Whys 대화 등 비공개 프로세스는 원문에 있는 사실(SCADA 정보과부하, 이메일 알림 방식, 승인/거부 구조 등)에 근거해 학습 목적으로 합리적으로 재구성한 것이며, 실제 발화 기록이 아니다.
> 출처: [Palantir Impact — Jacobs](https://www.palantir.com/impact/jacobs/) (2026 접속)
> ⚠️ **원문 자체의 수치 불일치(적대적 검증으로 발견):** 원문은 헤드라인에 "20% plantwide power savings"라고 쓰면서, 동시에 "~2,000 → ~1,500 kWh/백만갤런"이라고도 쓴다. (2,000-1,500)/2,000 = **25%**이지 20%가 아니다 — 팔란티어 1차 자료 안에서도 수치가 서로 안 맞는다. 아래 본문의 "20%"는 원문 헤드라인을 그대로 인용한 것이며, 실제 절감폭은 20~25% 사이 어딘가로 봐야 한다.

- **도메인:** 산업 운영 / 수처리(water treatment)
- **날짜:** 2026-09-08
- **한 줄 요약:** 이미 최적화된 수처리장에서 오퍼레이터의 감(gut) 기반 블로워 운전을, 예측 모델 → 이메일 추천 → 오퍼레이터 승인/거부라는 결정 루프로 전환해 전력을 절감한다.

## 0단계 · 시작 체크리스트 — 8원칙 (Principles Check)

> 상세: [../../knowledge/04-problem-solving-principles.md](../../knowledge/04-problem-solving-principles.md). "(소스 근거)"는 원문에 명시된 사실, "(불명)"은 원문만으론 확인 불가.

- [x] **1. 사용자가 되었나** — (소스 근거) "노이즈 많은 SCADA + 정보과부하로 감에 의존" 이라는 현장 사정이 구체적으로 서술됨. 다만 이게 실제 겐치겐부츠였는지 사후 마케팅 서술인지는 원문만으론 확정 불가.
- [x] **2. 건물 밖으로 나갔나** — (소스 근거) "오퍼레이터의 도구는 삶을 단순하게, 현장 워크플로에 맞춰야 한다"는 요구가 명시적.
- [ ] **3. 중개 계층이 없나** — (불명) 매니저-데이터사이언티스트 관계의 조직 구조가 원문에 안 나와 미체크.
- [x] **4. 작동 코드로 반복하나** — 공장 전체가 아니라 단일 사이트(Agua Nueva) PoC로 시작, 이후 확장 명시.
- [x] **5. 자갈길 먼저인가** — 전력 최대 소비원인 블로워 *하나*의 서브시스템만 우선 최적화, 전체 자동화가 아님.
- [x] **6. 결정으로 잇나** — 산출물이 대시보드가 아니라 "이메일 추천 + 오퍼레이터 승인/거부"로 귀결.
- [x] **7. 결과에서 역산하나** — (추정) kWh/백만갤런이라는 명확한 결과 지표가 보고되긴 하나, 원문은 "이 지표에서 역산해 설계했다"는 **설계 과정**을 직접 진술하지 않는다. 결과 지표의 존재로부터 합리적으로 추정한 것.
- [ ] **8. 복리인가** — 이 사이트 안에서는 거부+피드백 루프가 모델을 개선하지만(복리), "다른 Jacobs 현장·고객사로 확장"은 선언만 있고 구체 메커니즘은 원문에 없어 미확정.

## 1단계 · 몰입 (Immerse) — 현실 지도

- **누가** 결정: 사이트 오퍼레이터가 매일 블로워 설정값(운전 강도)을 조정.
- **무엇을** 근거로: SCADA 화면의 실시간 신호 + 오퍼레이터의 경험적 감(gut). 원문: "정보 과부하 상태에서 실행 가능한 인사이트를 뽑기 어려워 감(gut)에 의존한다."
- **실제 프로세스:** "이미 최적화된 플랜트"라는 전제에도, 블로워 운전은 리딩 인디케이터가 아니라 이상 발생 후 대응하는 반응형 패턴이었다.
- **사실 확인(원문 근거):** 오퍼레이터가 필요로 한 건 "더 강력한 분석 도구"가 아니라 "현재 워크플로에 꽂히는, 삶을 단순하게 만드는 도구"였다 — 요구를 있는 그대로 물었을 때 나온 답에 가깝다(Mom Test 취지와 부합).

### 숨은 곳 3가지
- 📌 **문서화 밖 결정:** 오퍼레이터마다 "이 정도 암모니아 수치면 블로워를 올린다"는 감각적 기준 — 표준 규칙으로 문서화되지 않음.
- 📌 **기록 안 되는 데이터:** 오퍼레이터가 왜 특정 설정을 선택/거부했는지(암묵지)가 시스템에 남지 않아 모델 개선에 못 쓰임.
- 📌 **하중 임시방편:** SCADA 알람에 오퍼레이터가 매뉴얼로 대응하는 것 자체가 사실상 "제어 시스템" 역할을 대신하고 있었다 — 공식 자동화가 아니라 사람이 그 공백을 메우고 있었음.

## 2단계 · 문제 정의 (Frame) — 문제 진술서

- **5 Whys** (재구성):
  1. 왜 전력 낭비가 있나? → 블로워가 실제 필요보다 비효율적으로 운전된다.
  2. 왜 비효율적으로 운전되나? → 암모니아 수치 같은 리딩 인디케이터를 실시간 반영 못 하고 감으로 조정한다.
  3. 왜 감으로 조정하나? → 관련 데이터(센서·랩·CMMS·재무)가 흩어져 있어 오퍼레이터가 한 번에 못 본다.
  4. 왜 흩어져 있나? → 각 데이터가 SCADA/랩/CMMS/Oracle 등 서로 다른 시스템에 사일로화돼 있다.
  5. 왜 사일로화됐나? → **예측 모델의 출력을 오퍼레이터 워크플로까지 잇는 통합·표준화 계층(온톨로지)이 없었다.**
  - **근본 원인:** 센서/데이터의 부재(기술)가 아니라 **통합·전달 경로의 부재(조직/시스템)** — 데이터는 이미 존재했다.
- **리프레이밍:**
  1. *지금 문제:* "공장을 어떻게 완전 자동화할까?"
  2. *달리 보기:* 이미 최적화된 공장이라 완전 자동화는 과잉이다 — 진짜 병목은 전력을 가장 많이 먹는 단일 서브시스템(블로워)의 결정 지연이다.
  3. *더 나은 문제:* "블로워 설정 결정을, 오퍼레이터의 기존 워크플로(플래닝 미팅 리듬) 안에서 어떻게 데이터 기반으로 만들까?" ← 채택.
- **문제 진술:** 블로워 운전 결정이 실시간 예측 데이터가 아니라 오퍼레이터의 감에 의존해, 회피 가능한 전력·컴플라이언스 리스크가 남아있다.
- **연결되는 운영상 결정/행동:** "블로워 설정값을 지금 바꿀 것인가"라는 하루 2회 반복되는 운영 결정.
- **성공 지표:** kWh / 백만 갤런 처리량(전력 원단위), 컴플라이언스 위반(벌금) 건수.
- **실제 제약:** 원격 데이터 사이언티스트 체제(현장 비상주), 오퍼레이터가 최종 결정권을 유지해야 한다는 조직적 요구(자동 집행 불가), 다중 레거시 시스템 통합.
- **옳은 문제인 근거:** 전력비가 운영비 핵심 변수이자 오퍼레이터의 매일 결정과 직결 + 측정 가능(kWh) + 정치적으로 실행 가능(오퍼레이터의 통제권을 뺏지 않고 보조하는 설계라 저항이 적음).

## 3단계 · 온톨로지 스케치 (Model)

> ⚠️ 아래 Object/Link/Action Type은 **이 실습을 위한 우리의 모델링 연습**이다. Jacobs가 Foundry에서 실제로 이렇게 스키마를 짰다는 검증된 사실이 아니다 — 원문은 "operator usage, electricity consumption, model error and drift를 온톨로지로 추적한다"는 수준으로만 언급하며, 구체적 Object/Action 이름은 공개하지 않았다.

### Object Types
| Object Type | 주요 Property | 의미 |
|---|---|---|
| Blower (블로워) | 설정값(set point), 현재 전력소비 | 제어 대상 장비 |
| AerationBasin (폭기조) | 암모니아 예측치, 컴플라이언스 기준치 | 공정 상태 |
| Recommendation (추천) | 추천 설정값, 발송 시각, 상태(대기/승인/거부) | 모델→오퍼레이터로 가는 결정 단위 |
| Operator (오퍼레이터) | 근무조, 피드백 이력 | 최종 결정권자 |

### Link Types
| From | Link | To | 의미 |
|---|---|---|---|
| AerationBasin | generates | Recommendation | 예측 모델이 폭기조 상태로부터 추천을 생성 |
| Recommendation | targets | Blower | 추천이 적용될 장비 |
| Operator | reviews | Recommendation | 오퍼레이터가 승인/거부 |

### Action Types
| Action | 무엇을 바꾸나 | 어떤 결정을 실행하나 |
|---|---|---|
| sendRecommendation | Recommendation 생성, 상태=대기 | 모델 예측을 오퍼레이터에게 전달 (플래닝 미팅 시각에 맞춤) |
| approveRecommendation | Blower.setPoint 갱신, Recommendation.상태=승인 | 오퍼레이터가 추천을 실행 |
| rejectRecommendation | Recommendation.상태=거부, 피드백 텍스트 기록 | 오퍼레이터의 예외 판단을 시스템에 기록 → 모델 재학습 신호 |

> 포인트: **rejectRecommendation**이 없으면 "왜 오퍼레이터가 거부했는지"라는 암묵지가 또 소실된다(1단계 숨은 곳 2). 이 Action이 "감(gut) 기반 예외 판단"을 시스템으로 끌어들이는 지점 — [knowledge/03 §2](../../knowledge/03-ontology.md)의 "끊어진 루프를 닫는다"가 여기서 구체화된다.

## 4단계 · 자갈길 구축 (Build) — 최소 해결책

- **접근:** 공장 전체 자동제어(고속도로)가 아니라, 전력 소비 1위 서브시스템(블로워) 하나만 예측+추천(자갈길).
- **산출물(원문 기반 재구성):** 센서·랩·CMMS·재무 데이터를 Foundry로 통합 → 암모니아 예측 모델 → 컴플라이언스 기준 대비 → 사람이 읽을 수 있는 이메일로 추천 → 오퍼레이터의 **기존 플래닝 미팅 시각(하루 2회)**에 맞춰 발송.
- **지탱하는 결정/행동:** 오퍼레이터의 "지금 블로워를 조정할까" 결정.
- **실제 제약을 어떻게 다뤘나:** 오퍼레이터의 통제권을 뺏지 않기 위해 자동 집행이 아니라 "추천 + 승인/거부" 구조로 설계 — 신뢰 구축과 조직적 수용성을 동시에 노림. 새 대시보드를 만들어 "가서 확인하라"고 강요하는 대신, 이미 있는 워크플로 리듬(미팅)에 도구를 끼워 넣었다.

## 5단계 · 패턴 추출 & 회고 (Extract)

- **반복될 추상:** "감(gut)에 있던 암묵지를 빼앗지 않고, 그 판단이 일어나는 기존 워크플로 리듬(여기선 플래닝 미팅) 안에 데이터를 끼워 넣는다" — 병원 회진, 콜센터 교대, 창고 피킹 등 어디든 반복 가능한 패턴.
- **재사용 가능한 기본요소로 승격할 것:** "예측 → 사람이 읽는 알림(기존 루틴에 맞춤) → 승인/거부 피드백"이라는 3단 구조를 템플릿으로.
- **무엇을 배웠나:** "전체 자동화"가 아니라 "레버리지가 가장 큰 서브시스템 하나 + 사람의 최종 결정권 유지"가 절감 효과와 조직적 채택 가능성을 동시에 잡았다.
- **다음엔 무엇을 다르게:** 이 케이스는 원 소스에 없는 정보(실제 5 Whys 인터뷰, 다른 사이트로 확장하는 구체 메커니즘)가 많다 — 실제 케이스라면 이 부분을 직접 현장 인터뷰로 채워야 한다.
- **걸려든 안티패턴:** 원문 자체는 안 걸렸지만, 이 자료를 학습에 쓸 때 "결과 수치(20% 절감)에 안주해 프로세스를 재구성 안 하는" 유혹이 안티패턴이다 — 그래서 이 문서는 수치보다 "왜 이메일이고 왜 승인/거부 구조인가"에 집중했다.
- **8원칙 재채점** (0단계 대비): 3번(중개 계층)과 8번(복리·다른 현장 확장)이 원문 정보 부족으로 확정 불가 — 실제 현장이라면 직접 확인해야 할 지점.
